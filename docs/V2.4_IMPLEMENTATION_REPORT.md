# Ledger v2.4.0 实现报告 — 多人房间（Server-Authoritative + WebSocket）

> **版本定位：让 Ledger 从「本地单机」升级为「可联机的同一个世界」。**
> 采用「本地 / 自部署 Node WebSocket 房间服务器」方案，服务器权威持有唯一游戏状态，客户端通过序列化 Action 驱动同一局游戏，并在断线恢复、确定性回放、主动模拟三重保障下保证所有终端状态一致。

---

## 1. 修改了什么（按 Phase）

### Phase 1 · 房间领域模型 → `server/room/RoomManager.ts` + `src/network/protocol.ts`
- 分离 **Room / Lobby / GameSession** 三个生命周期：
  - `Room`：房间壳（玩家席位、准备状态、房间码、分享链接，房主/状态机）。
  - **Lobby**：仅用于开局前的准备/设局/载入阶段。
  - **GameSession**：开局后持有唯一权威 `GameStore`，负责 Action 串行分发与状态快照。
- 房间码：6 位短码，可转 `#/multiplayer?room=<code>` 邀请链接。
- 席位校验：非房主不能 Start；所有玩家 Ready 才能开局；改名/换职业/换颜色实时同步。

### Phase 2 · 通信协议 → `src/network/protocol.ts` + `server/protocol/validate.ts`
- `room_snapshot` / `lobby_snapshot` / `session_bootstrap` / `room_error` 等分为「权威广播」与「逐连接乱序安全」两类。
- **运行时协议校验**：`validate.ts` 对每条入站消息做结构校验，字段缺失/类型错误直接拒绝（含 `requestId` 必填、`playerId` 必填），防止手工构造非法 Action。

### Phase 3 · WebSocket 传输 → `server/transport/websocket.ts`
- 非阻塞双栈监听，`/ws` 升级 + `/rooms` HTTP bootstrap。
- 心跳/保活 + 半开连接探测，为断线回收提供依据。

### Phase 4 · 游戏会话管理 → `server/game/GameSession.ts`
- **服务器权威单一 Store**：开局创建唯一 `GameStore`，所有客户端 Action 汇总到服务器串行分发。
- **Action 串行 + 幂等**：`requestId` 去重，`actionLog` 按序记录。
- **turnContext / allowedActions** 由服务器派生并广播，UI 只是从服务器得知「我当前能做什么」。

### Phase 5 · Lobby / 开局 UI → `MultiplayerHomeView.vue` / `RoomLobbyView.vue`
- 创建/加入房间、昵称、职业/梦想/颜色选择、Ready、房主 Start。
- 份额/颜色唯一性校验；加入后默认未准备。

### Phase 6 · 共享游戏世界 → `MultiplayerGameView.vue` + `src/stores/multiplayer.ts`
- **同一 Pinia 契约 + 两套交互布局**（沿用 v2.3 的 Mobile/Desktop 分支原则）。
- 移动端(390px)纵向 Game Flow，无横向溢出；桌面端 Dashboard 形态。
- `pendingAction` → `allowedActions` 驱动按钮显隐；`isMyTurn` 决定「谁可以提交 Action」。

### Phase 7 · 确定性 Replay / StateHash → `server/game/headlessStore.ts` + `GameSession.ts`
- `createGameHost({ seed })` 复位确定性 `defaultRandom`，使「相同 seed + 相同 actionLog ⇒ 相同状态」成立。
- `GameSession` 累积 `actionLog` 与 `eventLog`（`GameEventRecord`）、捕获 `initialState`，提供 `getReplay()` / `verifyReplayIntegrity()` / `getFinalResult()`。
- `game_finished` 广播附带 `finalStateHash / actionCount / eventCount / replayHash`。
- UI 常驻 **StateHash 同步指示**（`mp-state-hash`），多端应显示同一 8 位哈希 —— 作为三端同步质量的核心可观测信号。
- 单测 `v24-replay.spec.ts` 验证确定性回放、回放完整性、replayHash 稳定。

### Phase 8 · 自动对局模拟 → `scripts/multiplayer-sim.ts`
- 2/3/4 人 × 5 种子 × 保守/进取策略共 30 局无头对局，验证 **无死锁 / 无状态分歧 / 无 NaN / 无不变量违规**。
- 更高预算（4000 动作）下连续完整对局，验证可正常走向结局（见 §4）。

### Phase 9 · 断线 / 非法 Action 失败测试 → `v24-reconnect.spec.ts` + `v24-gamesession.spec.ts`
- **断线恢复**：会话令牌重连（roomId+sessionId+token）→ `reconnect_snapshot` 恢复席位；当前玩家断线→房间 Pause，重连→Resume。
- **非法 Action**：非当前玩家（`NOT_YOUR_TURN`）、当前状态不允许（`INVALID_ACTION`）、未知动作类型、缺 `requestId`、重复 `requestId`（幂等）。
- **游戏结束后 Action**：会话结束后继续提交 → 被服务器以 `INVALID_ACTION` 拒绝。

### 本次新增/修复
- **协议动作 `skip_stock_sell`**：修复「股票卖出轮询（`stock_sell_opportunity`）只有 `sell_opportunity`、轮到未持股/放弃的响应者时无法推进」的多人协议缺口 —— 新增放弃动作，推进到下一响应者（`GAME_ACTION_TYPES` 26→27，`action-contract.spec` 同步更新）。

## 2. 为什么这么修改

| 决策 | 动机 |
|------|------|
| Server-Authoritative（服务器权威状态） | 服务器持有唯一权威 Store，客户端只提交意图，天然避免状态分歧；三端 StateHash 必须一致。 |
| 复用客户/服务器同一套 Pinia Store | 服务器通过 `nodeShim.ts`（内存 localStorage）+ `createGameHost({seed})` 在 Node 中实例化同一个 `useGameStore`，业务逻辑零重写，保证离线/联机同规则。 |
| Action 串行分发 + `requestId` 幂等 | 客户端随机延迟/重发不产生状态漂移，统计到 `actionLog` 可确定性回放。 |
| 房间/大厅/会话三态分离 | 各阶段状态机独立，避免「开局后还能改席位」等一致性漏洞。 |
| 确定性 seed 回放 | 《敏捷复盘》要求每局可重放；`seed+actionLog` 即可在本地重建任一局。 |
| StateHash 常驻可见 | 让「同步状态」成为面向三端的一等公民，自动化测试据此断言一致（E2E 断言 `hashA === hashB`）。 |
| 新增 `skip_stock_sell` | 股票卖出是多玩家轮询子状态，必须给「不卖」一条合法推进路径，否则多人对局会真死锁（模拟器实测捕获）。 |

---

## 3. 复用的已有能力

- **同一套 `useGameStore`（`src/stores/game.ts`）** 在两个环境复用：浏览器原生 / 服务器 `nodeShim` + `createGameHost`。
- `engine/stateHash.ts`：确定性 `StateHash` 计算（服务器/客户端共用同一算法）。
- `engine/contract.ts` 的 `GameAction` / `GAME_ACTION_TYPES`：联机动作与单机动作同构。
- 确定性 `randomSource` / `engine/boardLayout.ts` / 交易与财务引擎：全部复用，服务器不重写业务。
- 单机 `pendingAction` / `allowedActions` 状态机：由服务器派生并广播，UI 只渲染。

## 4. Simulation：多人对局自动验证（确定性 seed）

`npx tsx scripts/multiplayer-sim.ts`

### 4.1 核心质量指标（2/3/4 人 × 5 种子 × 保守/进取，30 局，800 动作预算）

| 指标 | 结果 | 解读 |
|------|-----:|------|
| 死锁（`deadlock`） | **0** | 无 `pendingAction` 空转 |
| 状态分歧（`divergence`） | **0** | `verifyReplayIntegrity` 全通过，回放可重建权威状态 |
| NaN（`NaN`） | **0** | 无非法数值飘移 |
| 不变量违规 | **0** | 资金/净资产/资产守恒等断言全绿 |
| 分人数表现 | 2P/3P/4P 各 10 局全 0 异常 | 人数不引入额外风险 |

> 800 动作预算下游戏未走完（平均 100.2 回合），符合对局时长特征；**目标是对局中段验证，不要求收敛**。

### 4.2 完整对局收敛（2 人 × 3 种子 × 4000 动作预算）

| 指标 | 结果 |
|------|-----:|
| 完成率 | **6 / 6（100%）** |
| 平均回合 / 平均动作 | **564.2 / 3238.3** |
| deadlock / divergence / NaN / invariants | 0 / 0 / 0 / 0 |

> deterministic 重建：多回合后 `相同 seed + 相同 actionLog` 可完整重建权威状态（`v24-replay.spec` 断言 `verify.passed === true`）。

## 7. 已知问题

1. **对局时长长**：多人一局需数百回合才会自然收敛（2 人约 564 回合），中场 `save/join` 跨场续局尚未在本轮覆盖（断线**瞬时**恢复已覆盖，跨场重进做会话续局可在 v2.4.1 补足）。
2. **服务器宽松类型提示**：`server/**` 经 `vue-tsc` 之外的独立 tsconfig 运行，存在若干历史遗留的宽松类型签名提示（tsx 运行时无碍）。建议后续用 `@ts-expect-error` 或收窄签名收敛。
3. **`skip_stock_sell` 语义**：放弃动作直接推进到下一响应者，不做「本轮已放弃」的持久化标记；若同一位响应者在同一次轮询中被再次轮到仍可再卖（与单机「每次轮询最多响应一次」的语义有轻微差异），可在 v2.4.1 加每轮 `responded` 去重。
4. **老存档 / 未来 schema**：多人对局使用 `schemaVersion` 兼容单机存档；多人会话状态不与单机存档互写，避免跨模式污染。

## 8. 下一版本建议（按优先级）

1. **对局续局**：断线/刷新后不仅「瞬时恢复」，还能跨场（重新进入房间）续接同一局 —— 依赖已完成的 `getReplay()` + `replayHash`，可直接回放续局。
2. **`skip_stock_sell` 每轮去重 + 响应超时**：给轮询加单轮去重与超时自动跳过，避免「某人长时间不响应阻塞全场」。
3. **房间邀请链 / 历史战绩**：分享链接落地成邀请卡片；`game_finished` 已含 `replayHash`，可在房间页沉淀「战绩 + 回放入口」。
4. **服务器类型签名收敛**：把 `server/**` 的遗留宽松类型收窄，接入独立 CI type-check。
5. **v2.5 AI / Strategy Simulation**：将 `multiplayer-sim` 的线路策略替换为更真实的决策 bots，输出多人对局的平衡空间报告。
